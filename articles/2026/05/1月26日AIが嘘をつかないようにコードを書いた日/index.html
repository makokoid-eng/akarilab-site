1月26日、AIが嘘をつかないようにコードを書いた日

2026-05-13 · note 原文

連載「触り始めて9ヶ月の記録」第10話

第9話で書いた「20回 push の日」（2025年11月5日）から、82日後の話を書く。

11月5日、自分は1日で20回 push して、ようやくコードに馴染み始めた。

そこから約3週間 repimemo の調整を続けたあと、12月はほとんど開発の手が止まった。本業の年末繁忙期で、コードを触る余裕がなかった。git log にも、12月のコミットは11個しか残っていない。

年が明けて、2026年1月。

1月25日までは、まだ静かだった。

そして、1月26日。

その日、自分は repimemo に19個のコミットを積んだ。

12時06分から21時49分まで、9時間43分。

その19コミットの中に、いま振り返っても決定的だったコミットがある。

21:26 fix: prevent action fabrication and praise customer traits safely

この日、自分はAIに「いい感じの文章」を書かせるだけでは足りないことを知った。

AIが嘘をつかないように、コードで止める必要があった。

<!-- ここから先は有料 -->

"prevent action fabrication" が何を防いでいたか

"prevent action fabrication"

直訳すると、「動作の捏造を防ぐ」。

これは、AIに返信文の下書きを作らせたとき、AIが勝手に「今日は花束を贈りました」「先日のディナーは楽しかったです」のような、実際には起きていない出来事を書いてしまう問題への修正だった。

repimemo というのは、夜の店舗で働く人が、お客様への返信メッセージの下書きをAIに作ってもらうためのLINE Botだった。

お客様から「先週はありがとう」とLINEが来る。

ユーザーは、お客様について残しているメモ（好み・最近の会話・誕生日など）をもとに、自然な返信を作りたい。

そこでAIに下書きを任せる。

でも、AIは自然な文章を書こうとして、勝手に文脈を足してくる。

「来週も楽しみにしています」 「この前話していた京都の話、また聞かせてくださいね」

そんなことは、ユーザーは一言も書いていない。

AIが、自然に見せるために作った、嘘の文脈だった。

これをそのままお客様に送ってしまったら、困るのはAIではない。

ユーザー本人だった。

お客様は「あれ？京都の話なんてしたっけ？」と困惑する。下手をすると、信頼関係が崩れる。

自分のサービスを使った人が、自分のサービスのせいでお客様との信頼を損ねる。

それが起きてはいけなかった。

だから21時26分、自分は AI の出力を信用しすぎないためのコードを書いた。

1日19コミットの3つのテーマ

その日の19コミットを並べ直すと、3つのテーマで動いていたことが分かる。

ひとつ目は、UIを整えること。

日本語メニュー、クイック返信、キーボードを開く導線、helpコマンド、welcomeメッセージ。

ふたつ目は、AIの精度を上げること。

OpenAI draft generator、few-shot 学習（=AIに例を見せて文体を真似させる手法）、style_entries へのユーザーの文体保存。

みっつ目は、AIの暴走を止めること。

validate AI draft（=AIの出力を検証する）、prevent action fabrication（=動作の捏造を防ぐ）、adjustment quick replies（=ユーザーがすぐに調整できるボタン）。

この3つは別々の作業ではなかった。

「自分のためのおもちゃ」を作る段階から、 「他人が使っても壊れにくいもの」を作る段階に入っていた。

そして、その「他人が使っても壊れにくい」の中身は、ほとんどが「AIをそのまま信じないこと」だった。

22時44分の予感

連載第9話に書いた11月5日、自分の最後のコミットは22時44分だった。

あの日、自分は1日で20回 push して、「コードに馴染んだ」と感じた。

1月26日の最後のコミットは、21時49分。

21:49 fix: always show adjustment quick replies after draft (direct LINE API fallback)

「下書きの後に、必ず調整用のクイック返信を表示する。直接 LINE API で送信するフォールバック付き」。

これは、「もしAIが変な下書きを出しても、ユーザーがすぐに『調整する』ボタンを押せるようにする」という意味だった。

AIが嘘をついても、ユーザーがそれを止められる安全網を作る。

その日の最後のコミットに、自分はその安全網を入れて、パソコンを閉じた。

「触り始めの開発者」が、人生で初めて「自分のサービスを使う人の安全」を考えてコードを書いた夜だった。

11月5日の自分（20回 push でコードに馴染んだ）と、 1月26日の自分（19コミットで他人の安全を考えた）。

82日のあいだに、自分は「動くものを作る人」から「使われるものを作る人」に変わっていた。

もし、いまこれから始めるなら

ここからは、いまの自分が、当時の自分に伝えたいことを書く。

AIを使ったサービスを作るときは、AIを信用しすぎないコードを書く。

AIは親切で、流暢で、自然な言葉を返してくれる。

でも、AIは平気で文脈を足す。

起きていないことを、起きたことのように書く。

それを、人と人のあいだに置くなら、止める仕組みがいる。

prevent action fabrication

このコミットメッセージは、いま振り返ると、自分が「自分のためのおもちゃ」を作る人から、「他人に使われるサービス」を作る人に変わり始めた、最初の宣言だった。

これから個人開発を始める人に伝えたいのは、動くものを作ることの次には、必ず「他人に迷惑をかけないものを作る」が来る、ということ。

AIを使うなら、なおさらそうだ。

それが、44歳の触り始めの人間が、2026年1月26日の夜、9時間43分かけて学んだことだった。

次回は2026年2月、もうひとつのプロダクト「VAC」（本業の店舗QSCツール）を作り始めた話を予定しています。「現場21年のコードへの翻訳」が始まる回です。
