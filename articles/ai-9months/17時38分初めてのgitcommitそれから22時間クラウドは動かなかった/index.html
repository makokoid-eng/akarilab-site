17時38分、初めての git commit。それから22時間、クラウドは動かなかった

2026-05-13 · note 原文

連載「触り始めて9ヶ月の記録」第8話

2025年10月30日、17時38分。

repimemo というLINE Bot のプロジェクトに、自分は人生で最初の git commit を叩いた。

コミットメッセージはこう書いてある。

chore(repi): minimal webhook scaffolding

「chore」も「scaffolding」も、意味を知らないままChatGPTに教えられた通りに打った。

「repi」だけは、repimemo の頭文字で、自分でつけた略称だった。

このコミットの前、ちょうど42分前の17時前後に、Git のインストールが終わったところだった。

第7話に書いた通り、16時36分にVSCode を、16時56分にGit のインストーラーをダウンロードした。

そこから20分でGit をインストールし、ChatGPT に「git init はどう打つ？」「git add は？」「git commit は？」と聞きながら、最小限のコードを GitHub というサービスに置いた。

そのときの自分は、GitHub が何なのかも、push が何をしているのかも、ほぼ理解していなかった。

ただ、「ChatGPT が言う通りに打てば動く」という体験が、8月26日のEcho の夜以来、自分の中に積み上がっていた。

その体験を信じて、initial commit から1時間17分後、自動デプロイの workflow を追加した。

18:55 ci: add deploy workflow

これが、自分の人生で最初の「CI/CD」というやつだった。

<!-- ここから先は有料 -->

「ci: add deploy workflow」と書いた瞬間

CI/CD というのは、エンジニアの世界で「コードを書いたら自動でテストして自動で本番に上げる仕組み」を指す言葉だった。

GitHub には「GitHub Actions」という機能があって、これを使うと、git push するだけで、自動的にコードが Cloud Run（=Googleのサーバー実行サービス）に上がるようにできる。

その仕組みを、自分は人生で初めての commit から1時間17分後に組んでいた。

普通の感覚から言うと、これは飛ばし過ぎだった。

普通の入門者は、まず手動でデプロイ（=自分のコードをサーバーに上げる動作）を覚えて、何度かやってみて、それから自動化を考える。

自分はその手順を全部すっ飛ばして、いきなり自動デプロイから入った。

なぜか。

ChatGPT が「これが今のベストプラクティスです」と教えてくれたから、というのが正直なところだった。

そして、その「ベストプラクティス」が、22時間後の自分を、地獄に叩き落とすことになる。

19時30分、最初の「動かない」

ci: add deploy workflow の35分後、19時30分。

19:30 fix: add region variable

最初の fix コミットが入った。

何が起きていたかというと、自動デプロイのworkflow が動こうとした瞬間、「region 変数が無い」というエラーで止まっていた。

「region」というのは、Google Cloud のサーバーがどの地域にあるかを示す設定で、これがないと「どこの国のサーバーにデプロイするか分からない」というエラーが出る。

ChatGPT に聞いて、設定ファイルに region を1行追加した。

再度 push する。

また止まる。

19:40 fix: add token creator role

「token creator role」が無い、というエラー。

これは Google Cloud の権限の話で、デプロイをするためには「他のアカウントの代わりにトークンを作る権限」が必要、というやつだった。

ChatGPT に聞いて、権限を追加するコマンドを叩いた。

再度 push する。

また止まる。

19:48 fix: add token creator role

同じメッセージで、もう一回。

8分間で2回、同じ「token creator role を追加」コミットを打っている。

これは、最初の権限追加が正しく反映されていなかったか、別の場所にも同じ権限が必要だったか、どちらかだった。

19時48分、自分はここで一度寝た、と思う。

翌日13時、再開

翌日31日、13時07分、自分は再びパソコンの前に座っていた。

13:07 redeploy: IAM fixed

ここから、また地獄が始まる。

13:07, 13:14, 13:20, 13:36, 15:05, 15:17, 15:29, 15:51

9回のコミットが、2時間44分のあいだに続く。

13:14 final redeploy after cleanup 13:20 fix: add Cloud Run Service Agent role 13:36 fix: add Cloud Run Service Agent role 15:05 Configure gcloud CLI and modify deployment settings 15:17 fix: grant run.admin to CF admin robot 15:29 redeploy: grant run.admin to CF admin robot 15:51 redeploy: run.admin + actAs granted to all actors

「Cloud Run Service Agent role」「run.admin」「actAs」「CF admin robot」

エンジニアでない人がここを読むと、たぶん呪文にしか見えない。

その通り、当時の自分にとっても呪文だった。

それぞれの単語の意味を、当時は全く理解していなかった。

ChatGPT に「またエラー出た。ログはこれ」とエラーを投げて、ChatGPT が「じゃあこのコマンドを叩いてください」と返してきて、それを叩いて、再度 push する。

これを9回、2時間44分のあいだ繰り返した。

15時51分、ようやく9回目のコミットを打ったあと、自分はパソコンを閉じた。

4日間の沈黙

ここから、git log の上では、4日間の沈黙が始まる。

10月31日 15:51 の後、次のコミットは 11月4日 13:10 だった。

11月4日 13:10 redeploy: confirmed CF admin robot roles

「confirmed」 = 確認した、という意味。

つまり、10月31日にやった権限設定が、Google Cloud に反映されるのに数日かかって、11月4日にようやく動いた、ということだった。

その4日間、自分が何をしていたか、git log には残っていない。

仕事もあった。本業のエリアマネージャーの仕事は、止めていなかった。

たぶん、ふつうにシフトを作って、売上を確認して、会議に出ていた。

でも、頭の中ではずっと、「なんで動かないんだろう」「何の権限が足りないんだろう」を考え続けていた、と思う。

そして11月4日の昼、ようやく Cloud Run が動き出した。

自分の作った LINE Bot のコードが、自分のパソコンを離れて、Google のサーバーの上で動くようになった、最初の日だった。

何が起きていたのか

いま、エンジニア的に振り返ると、これはよくある「GCP IAM 権限の初心者地獄」だった。

GCP（Google Cloud Platform）に何かをデプロイするには、いくつもの権限を、いくつもの場所に、正しい順番で設定する必要がある。

その権限の組み合わせが、ドキュメントを読んでもよく分からない。

ChatGPT に聞いても、ChatGPT は「たぶんこの権限が必要です」とは言えるが、確実な答えは出せない。

なぜなら、GCPの権限は、プロジェクトごと、リージョンごと、アカウントごとに、組み合わせが少しずつ違うから。

つまり、自分が22時間で14回のコミットを打ったのは、コードのバグを直していたわけじゃない。「権限が足りないというエラーを、足りていない権限を試行錯誤で探しながら、消していた」だけだった。

これは、コードを書く力の問題ではなかった。

クラウドの権限を理解する力の問題だった。

そして、これは、44歳の元・統括店長が、人生で最初の git commit から1時間17分後に踏み込んだ世界の、最初の壁だった。

ここから始まった

11月4日に Cloud Run が動き出したあと、自分は repimemo を本格的に作り始めた。

11月4日、5日の2日間で、LINE 署名検証 → Firestore（=Googleのデータベース）→ OpenAI 連携、という3つの機能を立て続けに実装した話は、次回（第9話）に書く。

ここで書いておきたいのは、10月30日17時38分の最初の git commit から、11月4日13時10分の「ようやく動いた」までの、約5日と19時間が、自分にとっての「最初のクラウドの壁」だった、ということ。

その壁の中では、コードの話ではなく、権限の話で詰まっていた。

その壁を越えた経験は、いま振り返ると、いちばん大事なステップだった。

もし、いまこれから始めるなら

ここからは、いまの自分が、当時の自分に伝えたいことを書く。

最初の git commit から、自動デプロイまでを1日でやろうとしない。

これは、自分の最大の失敗だった。

普通の手順は、こうだ。

  1. ローカル（=自分のパソコン）でコードを書いて動かす。
  2. それを GitHub に push する。
  3. 手動で1回、サーバーにデプロイする。
  4. 手動で動くのを確認する。
  5. 何度か手動デプロイを繰り返す。
  6. ようやく、自動デプロイを組む。

自分はこの中の 3, 4, 5 を全部すっ飛ばして、2 のすぐ後に 6 を組んだ。

その結果、コードのバグなのか、デプロイの設定の問題なのか、権限の問題なのか、何が原因か分からないまま、22時間 fix を打ち続けた。

もしいまから始めるなら、最初は手動デプロイで十分。

自動デプロイは、手動でデプロイの仕組みを完全に理解してから組む。

そうすれば、エラーが出たとき、「どこで詰まっているか」が見えるようになる。

10月30日17時38分から11月4日13時10分まで、5日と19時間。

その間、自分は「赤ちゃん開発者」として、クラウドの壁に体ごとぶつかっていた。

その経験は、いま振り返ると貴重だった、と素直に言える。

でも、もう一度やるとしたら、もう少し賢くやる、と思う。

最初は、手動で。

次回は2025年11月4日と5日、ようやく Cloud Run が動き出したあと、LINE と Firestore と OpenAI を1日で繋いだ話を予定しています。
