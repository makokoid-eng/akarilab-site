9時9分から22時44分まで、20回 push を繰り返した日

2026-05-13 · note 原文

連載「触り始めて9ヶ月の記録」第9話

2025年11月5日、9時9分。

前日（11月4日）の昼に、ようやくクラウドの権限地獄を抜けて、自動デプロイが動き出した、と第8話で書いた。

11月5日の朝、その続きをやっていた。

git log にはこう書いてある。

2025-11-05 09:09 feat: move line.js into repi-webhook and update webhook modules

「line.js を webhook ディレクトリに移して、各モジュールを更新した」というコミット。これがその日の最初の feat（=新機能）コミットだった。

それから13時間35分後の、その日の最後のコミットがこれだった。

2025-11-05 22:44 feat: full version with quick replies, safeReply, tolerant draft, summary test

「クイック返信、安全な返信、寛容な下書きコマンド、要約テスト込みのフル版」というコミット。

朝9時から夜22時45分まで、ほぼ14時間。

その間に、自分は20回近くの git push を打っていた。

何をしていたかというと、LINE Bot を「動くだけ」から「ちゃんとしたサービス」にまで仕上げていた。

<!-- ここから先は有料 -->

朝、step1 → step2 → step3 の機能爆発

朝の作業は、ある明確な順序で進んでいた。

09:09 feat: move line.js into repi-webhook and update webhook modules 13:47 feat(step2): Firestore learning & draft saving + line helper 14:37 feat(step3): OpenAI summaryDraft generation + firestore update

「step2」「step3」と書かれているとおり、ChatGPT に「LINE Bot を本格的にやるための3段階」を教えてもらいながら、それを1日で全部実装していた。

step1（朝9時の作業）は、LINE からのメッセージを安全に受け取るための「署名検証」だった。LINE のサーバーから来たメッセージなのか、第三者の偽メッセージなのかを、暗号で確認する仕組み。

step2（13時47分）は、Firestore（=Googleが提供するデータベース）への保存だった。LINE で受け取ったメッセージを、ユーザーごとに保存する。

step3（14時37分）は、OpenAI API を呼び出して、保存したメッセージを要約する機能だった。

つまり、午前9時から午後2時37分までの5時間半で、「受け取る → 保存する → AIで処理する」というBotの基本機能を、3つとも実装し終わっていた。

5時間半。

8月26日に初めて echo を返した日から、ちょうど71日後だった。

午後、CI まわりの修正連打

step3 が動いた20分後、コミット履歴の様子が変わる。

14:56 fix: add OPENAI_API_KEY env for Cloud Functions deploy 15:20 fix: add package-lock.json for CI 17:47 ci: add OPENAI key to deploy workflow + auth debug 18:10 chore(ci): remove jq write step; use setup-gcloud service_account_key 18:14 explicitly activate GCP service account for deploy 18:54 ci: SA user binding added 19:12 ci: trigger workflow run 19:20 ci: switch to google-github-actions/auth (no key.json echo)

午後3時から夜7時20分まで、ほぼ4時間半、CI（自動デプロイ）まわりの修正が連続している。

「OPENAI_API_KEY env」「package-lock.json」「service_account_key」「SA user binding」「github-actions/auth」

第8話で書いた「GCP IAM 権限地獄」の余韻だった。

step3 で OpenAI API を呼ぶようにしたら、今度は「OpenAI のキーが本番環境にない」というエラーが出て、それを直したら別の権限エラーが出て、というのが繰り返されていた。

ただ、第8話のときと違ったのは、エラーが出るたびに「何が起きているか」が少しずつ見えるようになっていたことだった。

「key.json echo」というメッセージで、自分でも「あ、Google Cloud のサービスアカウントの認証方式が古いから新しい方に切り替えよう」と判断できるレベルには、たった1週間で達していた。

これは、5日前の自分（10月30日の「token creator role」を意味も分からず打っていた自分）と比べると、本当に別人だった。

夜、UX を作り始める

19時20分以降、コミットのテーマがまた変わる。

20:07 feat: welcome (follow), help command, and draft saved replies 20:25 feat: immediate reply + push summary message 20:42 feat: immediate reply + push; tolerant draft command; help & welcome; debug log 20:52 fix: never abort on reply failure; save-then-reply; push fallback 21:58 feat: quick-reply menu + postback + session mode (draft) 22:17 feat: quick replies everywhere + safeReply + tolerant draft + async push 22:44 feat: full version with quick replies, safeReply, tolerant draft, summary test

「welcome」「help」「quick reply」「safeReply」「tolerant draft」

これらは、ユーザーが Bot と対話するときの体験を作る部分だった。

友だち追加されたら自動で挨拶する。help と打ったらメニューを返す。クイック返信（=タップで選べる選択肢ボタン）を出す。返信に失敗してもアプリが落ちないようにする。

ここに自分の現場の経験が、たぶん効いていた。

21年間、店舗運営をやってきた人間にとって、「お客様が初めて入ってきたとき、いきなり『何ですか』と返さない」というのは、染みついた習慣だった。

LINE Bot に friend 追加された瞬間に welcome メッセージが出る、というのは、エンジニア的な発想じゃなくて、店舗運営の発想だった。

夜の3時間で、その「店舗運営の発想」を、コードに翻訳していた。

なぜ20回 push できたか

ChatGPT との対話だけで、こんなことができたわけじゃない。

11月5日のあの1日、自分が ChatGPT と話していた頻度は、おそらく1時間あたり数十回。

「このエラー出た」と貼り付けて、「コードを修正して」と頼んで、貼り付け直して、デプロイして、エラーが出て、また貼り付けて、を1日中やっていた。

その繰り返しの中で、自分の中に何が積み上がっていったか。

「これくらいの修正なら自分でできる」という感覚だった。

朝9時の時点では、ChatGPT に書いてもらわないと何も触れなかった。

夜22時の時点では、ちょっとした fix なら「あ、これは多分この行を変えればいい」と自分で見つけられるようになっていた。

たった13時間で。

これは、たぶん、コードを「読む」のではなく、「触る」回数が、その日に20回近くあったからだった。

20回 push して、20回エラーを見て、20回修正をしたら、コードの一部は自分の手に馴染んでくる、ということが、その日に分かった。

ここから始まった3週間

11月5日のこの「20コミットの日」のあと、自分は1週間ほど repimemo の調整を続けて、それからしばらく開発の手を止める。

そのあとの12月は、本業のエリアマネージャーの仕事が年末で忙しくなって、コードはほとんど触れなかった。

repimemo を「人に使ってもらえる」状態にまで持っていくのは、年が明けて2026年1月の話だった。

その話は次回（第10話）にとっておくが、ここで書いておきたいのは、11月5日の20コミットの日が、自分にとって「コードに馴染んだ」最初の日だった、ということ。

その日まで、自分はコードを「外側から触る人」だった。

その日から、コードを「中まで入って触る人」になった。

もし、いまこれから始めるなら

ここからは、いまの自分が、当時の自分に伝えたいことを書く。

完璧なコードを1回でコミットしようとしない。

これは、当時の自分が ChatGPT に教わって、いちばん効いた習慣だった。

「小さく区切って」「頻繁にコミットして」「頻繁にデプロイして」「何が壊れたか早く見つける」。

1日に20回 push してもいい。むしろ、それくらい push したほうが、コードに早く馴染める。

そして、自動デプロイを組んでおくと、push した瞬間に本番でエラーが見える。本番で動かしながら直す、という乱暴なやり方が、最初のうちは一番学べる。

これは、エンジニア界の作法としては、たぶん少し荒い。ふつうは、ローカルでテストして、ステージング環境で確認して、それから本番、というのが筋。

でも、44歳の触り始めの人間にとっては、「動くものを毎時間更新する」という荒さが、たぶん一番効いた。

その荒さの中で、コードと自分の距離が縮まる。

20回 push の1日を、たぶん月に1回でいいから、自分に課してほしい。

それが、コードを「読む側」から「触る側」に移るための、いちばん速いやり方だった、と振り返って思う。

そして、もうひとつ、当時の自分が ChatGPT と20回近く往復したことから、学んだことがある。

AI は「代わりに書いてくれる存在」ではなかった。

「試行回数を増やしてくれる存在」だった。

44歳の自分が、エンジニアのバックグラウンドがないまま、1日に20回 push できたのは、AI が代わりに書いてくれたからじゃない。AI が一緒に試行回数を増やしてくれたから、自分の頭でも理解する速度が、ふつうの1日の何倍にもなっていた。

これは、AI を「コードを生成する道具」だと思っているうちは、たぶん手に入らない感覚だった。

AI を「試行回数の相棒」だと思った瞬間に、自分の学習速度が桁違いに変わった。

11月5日の朝9時9分から夜22時44分まで、13時間35分。

その13時間で、自分は人生で初めて「コードに馴染んだ」と感じた。

次回は2026年1月、repimemo を「人に使ってもらえる」状態にまで仕上げた話を予定しています。
