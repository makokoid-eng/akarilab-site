「GAS↔API↔LINE」。

文字どおりには、Google Apps Script、Cloud Run の API、LINE Messaging API、この3つを「↔」（=矢印）で繋いだ、という意味。

技術用語で書くと味気ない。

ただ、この日のことを実感ベースで書き直すと、こうなる。

「フォームに応募が入ったら、ぜんぶ自動で、自分の LINE に通知が届く仕組みが、初めて動き出した日」。

44歳の触り始めの人間が、「自分一人で、複数のクラウドサービスを跨ぐ自動連携を組んだ」最初の日だった。

なぜこの仕組みが必要だったか

hidamari は、子ども向けの AI 学習 Bot。

連載第12話で書いたとおり、4月11日にリポを切って、1時間で5機能を実装した、自分にとって4つ目のプロダクトだった。

4月の終わりから5月にかけて、自分はこの hidamari を、知り合いの親に少しずつ渡し始めていた。

「子どもに、勉強でAIを使うBotを作ったんだけど、試してくれない？」と聞いて、興味を持ってくれた親に、LINE で友だち追加のリンクを送る。

最初は、それで十分だった。

10人くらいまでは、自分が手作業で「友だち追加してもらって」「学年と教科書を聞いて」「設定して」「使い方を説明する」ということをやっていた。

でも、それを続けていくと、すぐに2つの問題が見えてきた。

ひとつは、自分の手作業の限界。10人を超えた時点で、すでに「申込み履歴」を見失い始めていた。

もうひとつは、本人を覚える必要が高すぎた。「あの人は何月何日に応募してくれた、あの人にはまだ使い方を送ってない」を全部自分の記憶でやっていた。

これは、本業の店舗運営で20年やってきた仕事と、構造は同じだった。

ただ、店舗運営なら自分は20年の経験があって、しかも一人で抱えなくて良かった。スタッフも、シフトも、システムも、何重もの仕組みがあった。

個人開発でモニターを募集するときは、それが全部、自分一人だった。

だから、5月9日の朝、自分は決めた。

「申込みから通知まで、自分の手を一切入れない仕組みを作る」。

GAS↔API↔LINE の3階層

「GAS↔API↔LINE」の中身を、もう少し丁寧に書いておく。

ひとつ目のステップは、Google Form。

Google が無料で提供している、アンケートフォームのサービス。誰でもブラウザだけで、5分くらいでフォームが作れる。

「お子さんの学年」「使っている教科書」「保護者の連絡先」みたいな質問を並べて、URL を発行する。

そのフォームに、応募してくれた親が回答を入力する。

ふたつ目のステップは、GAS（Google Apps Script）。

Google Form の送信ボタンが押された瞬間に、GAS のスクリプトが自動で発動する仕組みがある。これも Google が無料で提供している機能。

GAS のスクリプトの中で、自分は「フォームの回答内容を整形して、Cloud Run の API に送る」というコードを書いた。

エンジニアの世界では、これは10分の作業だ。

でも、44歳の触り始めの人間にとっては、「Google Form → GAS → 外部 API」という三段階の連携を、自分の頭の中で初めて組み立てたのが、5月9日だった。

そしてみっつ目のステップが、Cloud Run の API。

GAS から送られてきたデータを受け取って、Firestore（=Googleのデータベース）に保存して、自分の LINE に「応募がありました」と通知する。

これが、本業のシフト管理アプリで例えると、「アルバイトが希望シフトをWebで提出 → 店舗管理システムに登録 → 店長のLINEに通知」と、ほぼ同じ流れだった。

20年間、こういう仕組みを「会社の中の誰かが作ってくれたシステム」として、自分は使う側だった。

5月9日17時43分、自分はそれを、自分一人で組んでいた。

1日で繋がったこと

5月9日のこのコミットの前後、git log は意外と静かだ。

2026-05-09 17:43 feat(monitor): β版モニター応募連携を GAS↔API↔LINE で接続

このコミットの前後数日に、これに関連する fix コミットが連発しているわけじゃない。

これは、これまでの連載で書いてきた「22時間14回のコミット」（第8話）や「20回 push の1日」（第9話）とは、まったく違う質感だった。

格闘の日々は、自分が「何が動かないか分からないまま」エラーログと戦っていた日だった。

5月9日の1コミットは、自分が「何が必要か全部分かっている状態」で組んだ仕組みだった。

エラーは出なかった。何時間も詰まる場面もなかった。

組んで、デプロイして、フォームに自分でテスト送信して、自分の LINE に通知が来るのを確認して、コミット。

それだけで、その日の作業は終わっていた。

「自分の知らないところで動く」初体験

5月9日にこの仕組みを動かしてから、いまこの記事を書いている時点（5月13日）まで、4日。

実は、まだ応募者は少ない。一桁前半。

でも、その一桁前半が、自分の手作業ではなく、自動で、Google Form から自分の LINE に通知として届いていた。

その通知が、初めて自分の LINE に届いた瞬間。

自分の中で、何かが切り替わった。

「自分の作ったプロダクトが、自分の知らないところで、ちゃんと動いている」

それを、初めて、体感した瞬間だった。

それまでは、自分が動かして、自分が確認して、自分が直していた。

5月9日からは、誰かが応募ボタンを押した結果が、自分の知らないルートで自分に届いた。

ボタンを押した本人は、自分のことを知らない。

自分も、その人がボタンを押した瞬間を、知らない。

それでも、Cloud Run のサーバーは動き、Firestore にデータは入り、LINE に通知が届く。

これが「自分の手の中のおもちゃ」から「世の中に置かれたプロダクト」に切り替わる、いちばん最初の体感だった。

もし、いまこれから始めるなら

ここからは、いまの自分が、当時の自分に伝えたいことを書く。

自分の作ったプロダクトを、誰かに使ってもらう段階で、必ず「自動で繋がる仕組み」を組む。

手作業で募集と返信を続けると、20人を超えたあたりで自分が破綻する。

破綻する前に、Google Form と GAS と Cloud Run と LINE Messaging API を繋ぐ。

これらは、全部 Google と LINE が無料で提供しているサービスだった。

エンジニアが企業で組むような、何十万円もする業務システムと、構造としては変わらない。

ただし、無料で組むには、自分が触り始めて9ヶ月くらいの経験が要る、ということだった。

逆に言うと、9ヶ月、毎週日曜にコードを書き続ければ、誰でもここまで来られる。

そして、ここに来た日、初めて「自分の知らないところで自分のプロダクトが動く」という体感が訪れる。

その体感を一度味わうと、「もう手作業には戻れない」となる。

5月9日17時43分は、自分にとってその境目だった。

次回は最終話。「触り始めて9ヶ月、5プロダクト並走の今、見えてること」を書きます。
