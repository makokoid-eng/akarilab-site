# 公開デモページ 仕様と設計判断

最終更新: 2026-08-10

## PURPOSE

申し込み前の見込み客に、製品の中身をそのまま見せるための公開ページ。
本番アプリは非公開環境で運用しているため、その代替として営業導線の入口を独立して持つ。

---

## 1. なぜ作ったか

### 背景となった事故

助成金ポータルの本番環境 `https://akari-josei-portal.akarilab.chatgpt.site` は
ChatGPT Sites の **Private Site** としてデプロイされている。
Private Site はプラットフォーム側で全パスにサインインを強制するため、
アプリのコードが動く前に、匿名の訪問者は必ず ChatGPT のサインイン画面で止まる。

にもかかわらず、akarilab.org 側からは「公開ポータルを見る」というラベルで
この非公開URLへリンクしていた。**申し込み前の社労士が開いて、そこで終わっていた。**

非公開デプロイ自体は意図的な設計（労務情報を扱うため）。
事故だったのは、非公開URLを「公開ポータル」と名付けて営業導線に置いていたこと。

### 採らなかった選択肢

本番Siteを Public に切り替える案は却下した。
アプリ側で認証を要求しているページが1つも無く（`requireChatGPTUser()` が未使用）、
保護がプラットフォームのゲートだけに依存しているため、
可視性を変えた瞬間に案件管理・メンバー管理・請求のUIが匿名で開く。

代わりに、**本番と完全に隔離した静的な公開デモ**を akarilab.org 側に持つ構成にした。

## 3. 助成金ポータル デモの構成

### 見せる範囲を絞った根拠

`docs/SALES_FUNNEL.md`（助成金ポータル側リポジトリ）§6 の
「社労士へ見せるものは、ポータル全機能ではなく次の一画面に絞る」に準拠し、
以下の6項目だけを表示する。

```
顧問先名 / 現在の工程 / 次に確認すること /
未提出書類 / システムが拾った懸念点 / 社労士が最終判断する項目
```

全機能を並べた管理画面を見せると、社労士は「覚えることが多そう」と判断して離れる。

### サンプル顧問先3社

工程の違う3社をタブで切り替える。1社だけだと「たまたま上手くいった例」に見えるため。

| 会社（架空） | 工程 | 見せたいこと |
| --- | --- | --- |
| みらい製作所 | 社労士確認中 | 懸念点が2件立っている、判断待ちの状態 |
| サンプル運送 | 顧問先入力中 | まだ情報が揃っていない、期限が暫定表示 |
| たとえば介護サービス | 出力可能 | 全部揃って、あとは最終判断だけの状態 |

みらい製作所の懸念点は、実務で本当に効く2つを選んでいる。

- 転換前の賃金台帳に1か月分の欠落（賃金3%以上増額の確認に必要）
- 就業規則の施行日が転換日より後（施行 2026-06-15 / 転換 2026-06-01）

### できること／やらないこと／まだできないこと

3列に分けている。当初は「できること／まだできないこと」の2列だったが、
電子申請ポータル連携と給与計算は**今後もやらない**と決めているため、
「まだできない（いずれやる）」に混ぜるのは誤りだった。

- **やらないこと** — 受給可否の判定・保証／申請可否の最終判断／電子申請ポータル連携／給与計算／専門士業の業務の代替。締めは「最終確認は、必ず人が行う設計です。」
- **まだできないこと** — 公式Excel様式への完全自動転記／書類内容の自動プレチェック／メール自動リマインド／事務所内の細かい権限分け。締めは「こちらは順次対応していきます。」

「まだできない」は言い訳に聞こえるが、「やらないと決めている」は設計思想に聞こえる。
社労士から見れば電子申請と給与計算は踏み込まれたくない領域なので、
やらないと明言するほうが信用される。
`/makoto/services/grant-portal/` の「やらないことを先に明確にします」とも揃えた。

## 4. 勤怠OCR デモの構成

### 売りを「精度」に置かなかった理由

OCRは「読み取れます」と言っても信用されない。誤読は必ず起きるため。
売りは**要確認の出し方**に置き、3ステップで見せる。

| ステップ | 内容 |
| --- | --- |
| 01 届いた勤怠 | 店舗から写真で届いたタイムカードをCSSで模写。かすれ・公休の空欄・`2570` の誤記・「田代?」を最初から混ぜてある |
| 02 読み取り結果と要確認 | 12件中5件に要確認。修正できる画面である旨も添える |
| 03 出力 | 既存Excel・給与ソフト前段向けのCSVプレビュー |

03のCSVには「退勤を手入力で補正」「日跨ぎとして確定」と、
**人が直した痕跡**を残している。全自動に見せないため。

### 要確認の線引き

トップページ Updates の
「空欄日や曜日違いのようなノイズは強い要確認から外し、片打刻、時刻不正、時刻逆転、氏名不明など、
実務上見落としたくない確認に寄せています」という設計判断を、そのまま営業材料にした。

| 強い要確認にする | 静かに置いておく | 人が決める |
| --- | --- | --- |
| 片打刻 | 空欄の日（公休・欠勤） | 丸め・端数の扱い |
| 時刻逆転 | 曜日の表記ゆれ | 休憩の自動控除の有無 |
| 時刻不正（25:70 等） | 備考欄の手書きメモ | 深夜・残業の判定 |
| 氏名不明 | 枠外のはみ出し | 読み取り結果の最終承認 |
| 同一日の重複打刻 | | |

全部に警告を出すと結局ぜんぶ目視することになり、意味がなくなる。
この線引きが分かる相手にはそのまま刺さる。

## 5. サンクスページ

### なぜ必要だったか

本番(livemode)の決済リンク**6本すべて**が、決済完了後に
`https://akari-josei-portal.akarilab.chatgpt.site/billing/success?plan=...`
へリダイレクトしていた。この遷移先も非公開ゲートの内側のため、
**カードで支払った直後の顧客がサインイン画面で止まる。**

### 2ページに分けた理由

決済後の手順が製品ごとに違うため。

- 助成金ポータル → 事務所情報をもらい、環境を作り、顧問先1社分を仮登録する
- 勤怠OCR → **まず実際の勤怠サンプルを送ってもらい**、読み取れるか確かめる

### プランの出し分け

`?plan=` を読んで、プラン名と課金条件を切り替える。
値は既存の決済リンクが送っているものをそのまま使うので、
Stripe 側はリダイレクト先のURLだけ変えればよい。

| ページ | 対応する plan |
| --- | --- |
| grant-portal/thanks/ | `grant_portal_monthly_7980` / `sr_bundle_monthly_11000` |
| attendance-ocr/thanks/ | `attendance_ocr_small_monthly_1980` / `_standard_monthly_2980` / `_sr_small_monthly_4980` / `_sr_standard_monthly_5980` |

未知の値・欠落・`__proto__` のようなプロトタイプ汚染狙いの値は、
すべて既定表示にフォールバックする（`hasOwnProperty` で判定）。

## 6. 守るべき制約

デモページを触るときは、以下を絶対に崩さないこと。

1. **外部通信を入れない** — `fetch` / `XMLHttpRequest` を使わない
2. **本番を参照しない** — D1 / R2 / 本番API を呼ばない
3. **実データを載せない** — 会社名・氏名・書類・打刻はすべて架空
4. **断定しない** — 助成金は受給可否を、OCRは読み取り精度を保証しない
5. **本番Siteの `app/` 配下に置かない** — 非公開ゲートの内側に入り、また見られなくなる

1〜3が崩れると、これは「営業用デモ」ではなく「認証の抜け穴」になる。

## 8. 検証

`jsdom` で実DOMを構築し、スクリプトを実行して確認する。ブラウザ不要。

確認している内容。

- 3社／3ステップの切替が正しく描画されるか、選択状態が1つに保たれるか
- サンプルデータの整合（要確認の件数が、実際のフラグ行数・サマリ・本文の説明文と一致するか）
- `?plan=` の全パターンと、不正値のフォールバック
- 外部通信が発生しないこと（`fetch` を罠に差し替えて検出）
- 外部リソース読み込みがゼロであること（`script src` / `link href`）
- 非公開URLへのリンクが本文に残っていないこと
- 内部リンクが実ファイルとして存在すること（リンク切れ検出）
- sitemap の整合

> 本文の「6件に要確認」という記述が実データ5件と食い違っていたのを、
> この突き合わせで検出して修正した。数字は本文とデータの両方から取って比較すること。

**未実施**: 見た目のスクリーンショット確認。
Chromium がサンドボックスのネットワーク制限で取得できないため、レイアウトは目視で確認すること。
